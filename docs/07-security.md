# 07 · 威胁模型与安全

按「攻击者能拿到什么」排序，不按技术分类排序。

## T1 · 无限铸造（最高危）

**影响**：签名服务或 MINTER 角色被攻破 → 攻击者铸造任意数量稀有皮肤 → 抛售 → 整个资产经济归零，且**不可逆**。

**缓解（纵深防御，任何一层单独失效都不致命）**：

| 层 | 措施 |
|----|------|
| 合约 | `SkinRegistry.maxSupply` 硬上限，`consumeSupply` 原子递增，超限 revert。即使 signer 被完全攻破，也只能铸造到上限 |
| 合约 | `maxSupply` 只可下调不可上调，且改动经 Timelock 48h |
| 密钥 | 签名私钥在 KMS，服务无法导出 |
| 服务 | voucher 服务只接受 `rewardId`，所有业务字段从 DB 读，攻击者拿到 API 权限也无法指定 skinDefId |
| 服务 | 每日签名限额 + 单玩家限额，超限拒签并告警 |
| 监控 | 链上 mint 速率异常检测（对比 pending_rewards 的预期速率），偏差 > 20% 立即告警 |
| 应急 | `PAUSER_ROLE` 热钱包可即时暂停 mint（不暂停 transfer） |

**演练要求**：上线前必须做一次「signer 泄露」的桌面演练，明确谁在多久内能执行 pause、撤销角色需要几个签名者到场。

## T2 · 签名重放

**攻击**：拿到一个合法 voucher 反复提交；或把测试网签名拿到主网用。

**缓解**：
- EIP-712 domain separator 含 `chainId` + `verifyingContract`，跨链跨环境自动失效；
- 每个 voucher 有唯一 `nonce`（bitmap 存储），消费后置位；
- `deadline` 强制过期（建议 7 天）；
- Merkle 路径用 `index` bitmap 防止同一 leaf 重复领取。

**必须有的测试**：二次提交、改 chainId、超 deadline、篡改任一字段后重新提交 —— 全部断言 revert。

## T3 · 客户端伪造资产

**攻击**：改内存 / 改封包，让自己显示为持有传说皮肤，或在 loadout 里塞入未拥有的 tokenId。

**缓解**：
- 客户端上报的皮肤信息**一律不采信**，游戏服务器通过 `entitlement-check` 独立校验；
- 其他玩家看到的外观来自服务器下发，不来自该玩家客户端；
- 本地改内存最多骗自己（自己屏幕上看到假皮肤），无实际收益，不投入成本对抗。

## T4 · 女巫刷奖

**攻击**：批量注册小号 / 用机器人刷对局，套取可交易的皮肤 NFT。

这是所有「玩游戏赚资产」模式的结构性弱点，**必须在链下解决，链上无能为力**。

**缓解**：
- 奖励绑定 **playerId 而非钱包地址**，注册门槛（手机 / Steam 时长 / 邮箱验证）即女巫门槛；
- 反作弊评分未达阈值的对局 → `pending_rewards.state = 'held'`，人工复核；
- **高价值奖励延迟发放**（如赛季结束后统一 Merkle drop），给风控留出批量识别时间窗；
- 新账号有资格冷却期（如注册满 7 天且完成 N 局才具备领奖资格）；
- 单账号日/周奖励上限。

关键认知：**一旦 mint 上链就不可撤回**。所有风控都必须发生在 mint 之前，这就是为什么 `held → claimable` 这个人工闸门必须存在。

## T5 · 元数据 / 外观篡改

**攻击**：运营方（或攻破运营方的人）事后把稀有皮肤外观改差，或 CDN 被投毒。

**缓解**：
- `contentHash` 上链承诺，客户端下载后本地校验（见 06）；
- `updateContentHash` 经 Timelock 48h + 链上事件 + ERC-4906，变更公开可审计；
- 款式 `frozen` 后哈希永久锁死；
- 元数据同步 pin 到 IPFS，停服后仍可访问。

## T6 · 链重组

**攻击/故障**：L2 reorg 导致已确认的 mint 消失，而 inventory 里仍显示玩家拥有。

**缓解**：12 个确认才进入可用 inventory；indexer 逐块校验 blockHash 并支持幂等回滚（见 05）。待确认资产在 UI 中明确标记，且不可用于 loadout。

## T7 · 开箱概率作弊

**攻击**：运营方根据玩家身份/付费额动态调整掉落，或事后修改结果。

**缓解**：epoch 种子的哈希提前上链、结束后公布明文；掉落表哈希上链承诺。任何人可离线复算全部开箱结果并验证。

**合规提示**：中国大陆（网络游戏抽取概率公示要求）、比利时/荷兰（开箱可能被认定为赌博）、部分美国州、韩国等地对开箱有明确监管。**开箱功能的地区可用性必须在产品阶段就确认**，不是上线前才补。这条属于法务范畴，但直接决定 `CrateOpener` 是否需要地区开关。

## T8 · 私钥与运维

| 密钥 | 存放 | 权限 |
|------|------|------|
| `DEFAULT_ADMIN_ROLE` | Safe 3/5 多签 → Timelock 48h | 角色授予/撤销、合约升级 |
| `REWARD_SIGNER_ROLE` | AWS KMS（不可导出） | 只能签 voucher |
| `PAUSER_ROLE` | 热钱包（单签，值班可用） | 只能暂停 mint |
| 部署密钥 | 硬件钱包，仅部署时使用 | 部署后立即移交所有权给 Timelock |

- Safe 的 5 个签名者必须是**不同的人、不同的设备**，不能是同一人的 5 个地址；
- 至少 2 个签名者不在同一物理地点；
- 定期（季度）做一次多签可用性演练 —— 很多项目出事时才发现某个签名者的设备丢了。

## T9 · 第三方依赖

- **RPC 提供商**：至少两家（如 Alchemy + 自建节点），自动故障切换。单一 RPC 是常见的单点故障；
- **Paymaster**：预算耗尽或服务故障时降级为玩家自付，不静默失败；
- **市场合约（Seaport）**：我们不控制。玩家的 `setApprovalForAll` 授权给外部市场是标准风险，在 UI 中提示玩家定期检查授权。
